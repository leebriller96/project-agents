# 세 번째 샘플 기획 — 규모 축

두 샘플로 검증한 것과, 아직 검증하지 못한 것:

| 샘플 | 축 | 규모 | 결과 |
|---|---|---|---|
| library-sample | greenfield | slice 3 | 함정 탐지·게이트·RR 되먹임 동작 확인 |
| secu-sample | migration(차세대) | slice 3 | AS-IS 함정 18/18 포착, 파이프라인 자체 결함 7건을 뒤 단계가 포착 |
| **sample3(예정)** | **규모** | **slice 12~20** | 미검증 |

두 샘플 모두 **slice 3개**였다. 파이프라인의 규칙 대부분(웨이브 편성, 공통화 타이밍, RR 묶음, 컨텍스트 분할)은
slice 가 늘어날 때 처음으로 부하를 받는데, 그 부하를 아직 한 번도 받아 보지 않았다.

## 검증 가설

| # | 가설 | 깨지면 드러날 곳 |
|---|---|---|
| 1 | 3개 이상의 웨이브에서도 `depends_on` 위상 정렬과 병렬 규칙이 성립한다 | 2·4단계 |
| 2 | 공통화(3단계)를 **언제** 끼우는지가 규모에 따라 달라진다 (slice 3개면 마지막, 15개면 중간에 1회 이상?) | 3단계, 공통 후보 수 |
| 3 | RR 이 수십 건이 되면 `/refactor` 의 묶음 전략(3→2→4 순서)이 그대로 통하지 않는다 | /refactor |
| 4 | brief·slices.yaml 자체가 커져서 에이전트 컨텍스트를 압박한다 (slice 20개 × 요구사항 = brief 수백 행) | 0·1단계 산출물 크기 |
| 5 | 새 게이트 층(`gate.py`·축·추적)이 규모에서 **비용을 만들지 않는다** | 단계별 `cost` |
| 6 | 검증 축 요구(traits)가 slice 마다 다를 때 5단계 환경을 몇 번 세우는가 | 5단계 소요 |

## 구성 방침

- **도메인 수**: 5~6개 업무 영역, 영역마다 2~4 slice → 총 12~20. 영역 간 의존을 의도적으로 2~3개 만든다.
- **traits 분포**: `file-upload`·`transaction`·`counter`·`rich-text`·`auth`·`batch` 가 각각 최소 2개 slice 에 걸치게 한다
  (축별 검증 환경을 여러 slice 가 공유할 때 비용이 어떻게 움직이는지 보려는 것).
- **공통 후보**: 세 개 이상의 slice 가 같은 것을 필요로 하는 상황을 최소 5개 심는다(코드·상태 라벨·권한 판정·파일 저장·페이징).
- **모드**: greenfield 로 하되, 중간에 "이미 만든 slice 를 고쳐야 하는 요구 변경" 을 1회 투입한다(운영 중 고도화의 축소판).
- **함정**: 앞 두 샘플처럼 의도적 함정을 심되, **규모에서만 드러나는 함정**을 우선한다.
  - 두 slice 가 같은 테이블을 다른 이름으로 참조
  - 세 slice 가 같은 공통 코드가 필요한데 세부가 조금씩 다름(성급한 공통화를 유도)
  - 선행 slice 의 계약 변경이 후행 3개를 동시에 깨뜨림
  - 같은 요구사항 ID 가 두 slice 에 걸쳐 추적이 끊기기 쉬운 배치

## 측정 지표 (회차 간 비교용)

`pa-meta.cost` 와 `gate.py` 결과로 자동 집계할 수 있는 것만 지표로 삼는다.

| 지표 | 원천 |
|---|---|
| 단계별 소요·tool call·토큰 | `pa-meta.cost` |
| 게이트 FAIL 건수와 원인 훅 분포 | `gate.py check --format json` |
| 축 커버리지 공백(요구 축 대비 미충족) | `coverage-axis` 훅 |
| 추적 끊김 수 | `gate.py trace` |
| RR 수명 (발견 회차 → done 회차) | `rr.py list` + `iteration` |
| 확인 필요 항목의 평균 체류 단계 | `open-items.yaml` |
| slice 당 평균 비용 (3 slice 샘플 대비) | 위 지표 나눗셈 |

목표는 "잘 돌았다" 가 아니라 **어느 규칙이 규모에서 먼저 깨지는지**를 찾는 것이다.

## 대안 축 — brownfield

규모 대신(또는 다음으로) 검증할 축. 실무에서 가장 흔한 형태다.

- `mode: brownfield` — 운영 중인 코드베이스에 기능을 추가·수정한다. 지금 파이프라인에는 이 모드가 없다.
- 필요한 것: 0단계가 **기존 코드**를 brief 로 압축(AS-IS 인벤토리와 유사하되 TO-BE 가 같은 repo),
  1단계가 신규 slice 를 기존 구조에 **끼워 넣는** 분류, 2·4단계가 기존 컨벤션을 골격 대신 사용,
  3단계가 기존 공통 모듈을 존중(새로 만들지 않음), 5단계가 **회귀** 중심.
- 게이트 관점: 기존 테스트가 기준선이 되므로 `pa-meta.gates[].test_count` 의 **감소**가 곧 회귀 신호다.

## 착수 절차

1. `config/project.yaml` 의 `project.name` 을 sample3 로, `target_dir` 을 새 경로로 바꾼다 (secu-sample workspace 는 그대로 남는다).
2. `workspace/sample3/00_inputs/` 에 문서를 넣는다 — 요구사항·화면·테이블·환경. 함정은 문서 안에 심는다.
3. `/stage0` → `/stage1`(traits 필수) → 승인 → `/run --to 5 --dry` 로 계획 확인 → `/run --to 5`.
4. 회차가 끝나면 위 지표를 `docs/LESSONS.md` 에 표로 남기고, 깨진 규칙을 같은 회차에 고친다(`/rerun` 6항 업그레이드 의무).
